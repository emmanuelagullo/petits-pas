#+title: Préparer la migration des référentiels — #R3a

* Portée

La commande =diagnostiquer_referentiels= lit la base actuelle, sans correction,
import de YAML, création d'origine ou modification des médias. Elle prépare
#R3b ; elle ne certifie pas que la migration peut déjà être lancée.

Utiliser de préférence une copie restaurée de la base : la commande ne bloque
pas les écritures concurrentes et un rapport sur une base utilisée peut refléter
plusieurs instants. Utiliser les mêmes réglages de connexion que manage.py.

#+begin_src sh
python manage.py diagnostiquer_referentiels
python manage.py diagnostiquer_referentiels --ecole 1 --json
python manage.py diagnostiquer_referentiels --json --exiger-coherent > diagnostic-referentiels.json
#+end_src

Sans filtre, toutes les écoles sont examinées. Le filtre désigne une école par
identifiant ; une école inexistante échoue. Une base vide est acceptée.
L'option --exiger-coherent rend un code de sortie non nul en présence d'un
constat bloquant, après émission du rapport complet ; les avertissements seuls
ne provoquent pas cet échec. Le JSON a un numéro de format, pour distinguer
une évolution ultérieure de ses champs. Les listes contiennent les identifiants
du type d'objet annoncé par le code du constat, pas des noms ni du contenu privé.

Les codes partagés, compétences masquées et années ambiguës sont « à examiner » ;
l'absence d'origine est informative. Les autres constats sont bloquants pour
la reprise automatique proposée. La commande ne décide d'aucune correction.

* Limites importantes

Même une observation ayant une seule scolarité ne prouve pas son contexte
historique : une date ne reconstruit pas les états effacés. Le diagnostic ne
compare pas la base au YAML actuel pour inventer une filiation. Les volumes
incluent les traces retirées et les éléments inactifs, qui doivent être conservés.
Les identifiants du rapport restent à traiter comme des informations internes.

La commande ne lit pas les fichiers médias et ne vérifie pas leur existence.
Les protections de clés étrangères de la base sont supposées actives ; ce
rapport ne remplace pas un contrôle d'intégrité d'une sauvegarde. Avec --ecole,
les relations sont contrôlées à partir des objets propriétaires de cette école ;
utiliser le rapport complet pour couvrir les relations provenant d'autres écoles.
Aucune vérification de source versionnée n'est possible avant #R3b.

* Préparation de #R3b

Conserver le rapport d'une copie restaurée et les volumes de référence.
Examiner les blocages, les codes ambigus et les états sans année unique ;
consigner les décisions sans modifier une base réelle dans le cadre des essais.
La future migration doit reprendre les clés et les liens, conserver les objets
masqués et produire explicitement un état initial repris. Un diagnostic sans
blocage ne garantit pas une reconstitution historique complète.

Tests avec données fictives : lecture sans INSERT/UPDATE/DELETE, base vide,
filtrage d'école, école absente, doublon, masquage, état multi-années et relation
entre écoles. Aucun parcours enseignant nouveau : le Guide pratique ne change pas.

* Vérifications de livraison

27 tests réussis sur SQLite avec Django 6.1.1 : les 7 tests du diagnostic et
les 20 tests de présentation #T, après collectstatic. Contrôle des migrations :
aucun changement détecté. Syntaxe Python et espacement vérifiés. Application
git am contrôlée avant livraison. PostgreSQL et la suite complète non exécutés ;
les deux profils de CI devront compléter cette validation. Hugo et paquets
non reconstruits : aucun écran, page publique ou emballage n'est modifié.

* Première reprise expérimentale — #R3c1

Après la migration 0016 de #R3b, uniquement sur une copie restaurée et conservée
pour les essais :

#+begin_src sh
python manage.py migrate
python manage.py diagnostiquer_referentiels --exiger-coherent
python manage.py reprendre_referentiels --ecole 1 --appliquer-sur-copie
#+end_src

La commande refuse les incohérences bloquantes du diagnostic, puis reprend
atomiquement l'école demandée. Un nouvel appel ne réimporte pas l'état courant
et ne réécrit pas la version initiale. Les clés existantes et le suivi courant
sont conservés. Le contenu fourni (domaines, sous-domaines, attendus, compétences,
formulations) est photographié comme état initial local, sans filiation supposée
avec la trame YAML. Les réglages école/classe présents sont conservés avec une
mention explicite : ils ne reconstituent pas les anciennes présentations.

Les classes reçoivent une adoption initiale sans date historique inventée.
Les traces et traces communes reçoivent un contexte d'après leurs relations
actuelles. Les années de scolarité reçoivent des états explicitement inconnus,
sans recopier la réussite courante dans le passé. Une trace existante ne suffit
pas à déduire l'état final de l'année ; commentaires et photos ne sont pas touchés.
Le cas local de 602 observations ambiguës ne demande aucune qualification
manuelle : la reprise les conserve et n'invente pas d'états annuels.

Ce sous-jalon n'est pas la bascule des lecteurs et des nouvelles écritures.
Les écrans continuent d'utiliser les modèles actuels ; une nouvelle trace peut
encore ne pas avoir de contexte. Les références de photos photographiées ne
protègent pas encore leurs fichiers contre un nettoyage ultérieur. Ne pas
considérer cette copie comme une école déjà migrée pour l'usage quotidien.
#R3c2 devra fournir le lecteur et les écritures cohérentes, ainsi que la protection
des ressources, avant ouverture des fonctions #R4. La commande de reprise ne
se lance pas automatiquement au démarrage ou à la restauration d'un paquet.

Exécuter sans écritures concurrentes ; le verrou d'école coordonne les reprises
entre elles sur PostgreSQL, pas les services pédagogiques existants. Le drapeau
--appliquer-sur-copie est une déclaration de l'opérateur, pas une détection
technique du caractère fictif ou sauvegardé de la base.

Vérifications #R3b/#R3c1 : 34 tests SQLite réussis (fondations, reprise,
diagnostic et présentation #T), contrôle des migrations sans changement et
contrôle d'espacement. Les tests couvrent protection des observations,
immuabilité via save, adoption courante unique, état inconnu, contexte protégé,
reprise répétée sans effet, refus atomique des doublons et confirmation de copie.
La migration 0016 est appliquée par la création de la base de test. La migration
d'une sauvegarde de l'utilisateur et PostgreSQL restent à vérifier en #R3d/CI.

* Écritures contextualisées — #R3c2a

Après reprise de l'école, les nouvelles traces individuelles et communes
reçoivent l'usage de la base courante de leur classe. Une correction conserve
l'usage d'origine ; la personnalisation d'une trace commune conserve aussi ce
contexte. Modifier un état renseigne l'état connu de l'année de la scolarité
courante, sans réécrire les anciennes années. Ajouter une trace seule ne
transforme pas un état historique inconnu en réussite.

Une nouvelle classe d'une école reprise reçoit ses choix annuels lors de sa
première saisie, à partir de la version proposée de son année ou, à défaut,
de la version initiale reprise. L'ancienne classe n'est pas modifiée. Une
compétence masquée ou ajoutée directement en base sans adoption n'est pas
utilisable pour une nouvelle saisie contextualisée. Les anciens contextes
restent consultables et les corrections de traces gardent leurs droits habituels.

Une école non reprise conserve provisoirement les parcours précédents sans
contexte annuel. Initialisation et reprise automatique des nouveaux ateliers
restent à consolider avant la fin de #R3. Ce sous-jalon ne fournit pas encore
les écrans de choix de base ou de clôture. Il ne modifie pas les autorisations
pédagogiques existantes et n'attribue aucune réussite par correspondance.

* Lecteur par classe et conservation des ressources — #R3c2b

Les listes de compétences d'une classe reprise utilisent sa version adoptée,
avec ses identifiants existants, son ordre et sa structure. Une modification
directe d'un libellé du catalogue ne réécrit donc pas sa définition annuelle.
Le chargement YAML direct est refusé après reprise : l'adoption d'une nouvelle
version devra passer par #R4/#R8. Les écoles non reprises gardent le lecteur
précédent. Une compétence masquée ayant des observations visibles peut rester
au carnet ; le masquage ne détruit ni les traces ni le suivi.

Le service interne clore(utilisateur=..., classe=...) conserve la présentation
finale de la classe : structure, masquages, illustrations et phrases proposées.
Il requiert les droits actuels du responsable ou de la direction. La clôture
est répétable sans effet et bloque les nouvelles saisies d'états et réglages
collectifs ; les corrections de traces restent soumises aux droits existants.
Ce service n'est pas encore un bouton proposé aux enseignants.

Pour l'année courante, la clôture conserve le suivi effectivement connu à cet
instant. Pour une ancienne année reprise, elle n'emprunte pas une réussite
courante pour combler un état inconnu. Les états annuels déjà connus restent.
Les nouvelles années ne modifient pas les anciennes versions closes.

La migration 0017 conserve des références aux photos présentes dans les états
initiaux déjà repris ; la commande de reprise le fait aussi pour les reprises
suivantes. Les photos encore référencées échappent au nettoyage des médias
remplacés. À la clôture, les photos sont référencées sans duplication ; les
petits SVG fournis sont copiés dans les ressources privées pour ne pas dépendre
d'un remplacement futur du fichier distribué. Leur consultation exige un élève
et une classe du parcours autorisé ; aucun lien direct au stockage n'est publié.

La base et les médias restent à sauvegarder ensemble. Le service de clôture
peut laisser une copie de SVG non référencée si un stockage échoue après une
copie réussie : la transaction protège les relations en base, pas les écritures
sur un stockage externe. Le fichier orphelin est préférable à la perte d'une
image utilisée. L'édition exacte d'un PDF reste hors de ce périmètre.

* Consultation annuelle accessible — #R3c2c

Le carnet propose les années du parcours déjà autorisé, sans ouvrir un accès
à une autre scolarité. Le paramètre annee est conservé dans les choix et le
PDF ; une année absente ou interdite est refusée. Sans année choisie, le parcours
complet existant reste disponible. Pour une année antérieure choisie, le lecteur
utilise les états annuels et les traces de cette scolarité. Un ancien état
inconnu ne reçoit pas la réussite courante ; sa trace peut être affichée avec
la mention « État de cette année non retrouvé ». Les bilans sont limités à
l'année choisie. Aucun état historique n'est enregistré pendant cette lecture.

Les choix initiaux conservés lors de la reprise servent la présentation d'une
ancienne année non close, avec un avertissement sur leur portée. Les choix
clos utilisent les ressources et les états photographiés à la clôture, sans
réinterprétation depuis le suivi courant. Les accès aux photos annuelles
restent limités aux classes et années visibles dans le parcours autorisé.

La progression de la classe utilise les compétences de sa base visible, tant
pour le total que pour le nombre de réussites : une compétence masquée ne peut
plus faire dépasser le nombre de compétences proposées. La grille reprend le
libellé de la base de classe. Le Guide pratique documente la consultation
annuelle, sans annoncer le choix de base ou la clôture comme parcours accessibles.
