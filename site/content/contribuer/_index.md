Petits Pas se construit comme un bien commun. Contribuer peut vouloir dire
écrire du code, mais aussi décrire un geste de classe, relire un carnet,
éprouver un déploiement ou rendre une explication plus accessible.

Il n'est pas nécessaire de connaître Git, GitLab ou le développement logiciel
pour apporter un retour utile.

## Contribuer depuis le terrain

Les équipes pédagogiques peuvent notamment :

- décrire une situation quotidienne que l'outil devrait mieux accompagner ;
- signaler une étape inutile ou un vocabulaire peu naturel ;
- relire la présentation d'un carnet destiné aux familles ;
- comparer le parcours proposé avec leurs pratiques ;
- essayer la [démonstration publique]({{< relref "/demonstration/" >}}) avec
  des données exclusivement fictives.

Un retour n'a pas besoin de proposer déjà une solution. Décrire le contexte,
le résultat attendu et ce qui gêne aujourd'hui est souvent plus utile qu'une
spécification complète.

## Faire parvenir un retour

Lorsqu'une personne vous a présenté Petits Pas ou proposé de l'essayer, le plus
simple est de lui répondre par le canal habituel de votre échange. Un retour
oral, quelques lignes dans un courriel ou des annotations sur un carnet peuvent
ensuite être reformulés en besoins partageables, sans donnée personnelle.

Un moyen de contact simple sera ajouté à ce site pour permettre à chacun de
transmettre un retour, sans avoir à connaître les outils utilisés pour
développer Petits Pas.

## Contribuer à l'exploitation

Les DSI, collectivités et hébergeurs peuvent aider à :

- relire les hypothèses de la [présentation technique]({{< relref "/dsi/" >}}) ;
- expérimenter les profils de déploiement sur une plateforme différente ;
- éprouver les procédures de sauvegarde et de reprise ;
- préciser les exigences d'habilitation, de journalisation et d'exploitation ;
- identifier une dépendance implicite à un fournisseur.

## Contribuer au code et à la documentation

Avant de commencer une modification importante, consultez les
[issues existantes](https://gitlab.inria.fr/petits-pas/petits-pas/-/issues) ou
[ouvrez une issue](https://gitlab.inria.fr/petits-pas/petits-pas/-/issues/new)
pour partager le besoin et le périmètre envisagé.

Les corrections ciblées peuvent être proposées par une
[merge request](https://gitlab.inria.fr/petits-pas/petits-pas/-/merge_requests).
Le fichier
[`CONTRIBUTING.md`](https://gitlab.inria.fr/petits-pas/petits-pas/-/blob/main/CONTRIBUTING.md)
rappelle les licences et les vérifications à effectuer.

Les contributions utiles ne concernent pas seulement Python ou Django. Le
projet accueille également les améliorations portant sur :

- les textes et exemples ;
- l'accessibilité au clavier, sur mobile ou avec des technologies d'assistance ;
- les tests et les jeux de données fictives ;
- les procédures d'installation et d'exploitation ;
- la présentation des choix et de leurs limites.

## Les forges du projet

[GitLab Inria](https://gitlab.inria.fr/petits-pas/petits-pas) est la forge de
référence. Le code courant, les issues, les propositions de modification et
l'intégration continue y sont réunis.

Une [copie publique est également visible sur
GitHub](https://github.com/emmanuelagullo/petits-pas) pour faciliter la
découverte du projet. GitLab Inria demeure la référence : les signalements et
contributions techniques doivent y être ouverts afin de ne pas répartir les
échanges entre deux forges, et seule la version qui y est publiée est garantie
comme étant à jour.

## Ne jamais publier de données réelles

Une issue, une merge request, un journal de test ou une capture d'écran est
susceptible d'être public. N'y joignez aucun nom d'enfant ou de famille, aucune
photographie, production, observation, donnée d'établissement ou information
permettant d'identifier une personne.

Un problème doit être reproduit avec des données inventées et minimales. Si un
signalement révèle une vulnérabilité ou une information sensible, ne publiez
pas les détails dans une issue ordinaire. Le projet doit encore formaliser un
canal privé dédié avant tout déploiement de production.

## Licences des contributions

Le code est distribué sous licence `AGPL-3.0-or-later`. La documentation
publique originale est distribuée, sauf mention contraire, sous licence
`CC-BY-SA-4.0`.

Sauf accord explicite préalable, une contribution est proposée sous la licence
correspondant à sa nature. Son auteur conserve ses droits et confirme qu'il
peut publier ce qu'il apporte ; aucun transfert de copyright n'est demandé.

## Participer sans engager son institution

Un échange, un test ou une contribution ne constitue pas automatiquement une
approbation du projet par une école, une collectivité, une administration ou
un employeur. Les remerciements distingueront toujours une participation
effective d'un éventuel soutien institutionnel explicite.
