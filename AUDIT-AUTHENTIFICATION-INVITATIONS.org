#+author: Équipe Petits Pas

* Statut du document

Ce document consigne un audit des politiques d'authentification et
d'invitation actuelles de Petits Pas, les options envisagées pour les
faire évoluer vers un standard moderne, les décisions retenues et une
feuille de route par jalons.

Les décisions marquées =Ouvert= restent à trancher ; le reste engage
l'implémentation.

- =MODELE-IDENTITES-ET-AFFECTATIONS.org=

* 1. Constat — état actuel

** Ce qui est déjà solide

- Le modèle =comptes.models.Invitation= suit le pattern
  sélecteur/vérificateur recommandé pour les liens à usage unique :
  jeton haute entropie (=secrets.token_urlsafe(32)=) jamais stocké,
  seule son empreinte SHA-256 est en base, comparaison en temps
  constant (=secrets.compare_digest=). Expiration, état
  (=en_attente/acceptee/revoquee/expiree=) et verrouillage
  transactionnel (=select_for_update=) à l'acceptation sont corrects.
- Le lien d'invitation n'est révélé qu'une fois, via un message flash
  de session (=lien_invitation_creee=), jamais re-consultable ensuite.
- La migration =0009_supprime_mots_de_passe_partages= a retiré les
  mots de passe partagés par école (=mdp_enseignant=,
  =mdp_direction=) au profit d'identités individuelles
  (=Utilisateur= = =AbstractUser=), indépendantes des écoles —
  cohérent avec =POLITIQUE-AUTORISATION.org=.
- Fondamentaux Django propres : validateurs de mot de passe (dont
  longueur minimale 12), CSRF actif, cookies de session
  =HttpOnly=/=SameSite=Lax=/=Secure= conditionnés au HTTPS forcé,
  session courte (12h).

** Ce qui manque

| Manque                                  | Détail                                                                                    |
|------------------------------------------+--------------------------------------------------------------------------------------------|
| Envoi d'e-mail                          | Aucun =EMAIL_BACKEND= configuré ; le lien d'invitation est transmis à la main              |
| Récupération de mot de passe            | Prévue par =POLITIQUE-AUTORISATION.org= (administration, secours) mais aucune vue self-service implémentée |
| Vues de connexion réimplémentées        | =connexion()= et la branche =compte_existant= de =accepter_invitation_vue()= réimplémentent =authenticate()=/=login()= au lieu des vues Django standard |
| Anti-bruteforce                         | Aucun blocage après tentatives échouées                                                    |
| Audit des connexions                    | =journaliser()= exige un objet rattaché à une école ; les échecs de connexion ne sont pas tracés |
| UI du mot de passe                      | Champs =password= bruts, pas de bouton « afficher en clair », pas d'indicateur de robustesse |
| Authentification à deux facteurs         | Absente                                                                                     |

* 2. Options envisagées

** Brique d'authentification complète (=django-allauth=) — écartée

=django-allauth= apporte vérification d'e-mail, social login, 2FA
(=allauth.mfa=), gestion multi-comptes. Écarté parce que le modèle
=Invitation= de Petits Pas n'est pas un simple pré-compte : c'est un
lien invitation ↔ école ↔ future appartenance, avec des règles
d'autorisation propres. Adopter allauth reviendrait soit à contourner
son modèle d'invitation, soit à dupliquer à côté la logique déjà
écrite — pour un bénéfice marginal, la majeure partie de son poids
(vues, templates propriétaires, signaux) ne servant à rien ici.

** Brique d'invitation dédiée (=django-invitations=) — écartée

Même raisonnement : le modèle d'invitation du projet (lié à une
école, jeton haute entropie, empreinte seule stockée) est déjà plus
rigoureux que ce que gère ce package par défaut.

** Composition de briques standard Django — retenue

Combler chaque manque avec l'outil le plus proportionné, sans
réécrire le modèle métier existant :

- Envoi d'e-mail : backend SMTP natif de Django ; =django-anymail=
  facultatif pour les fournisseurs transactionnels qui le nécessitent.
- Mot de passe oublié : =PasswordResetView=/=PasswordResetConfirmView=
  de =django.contrib.auth.views=, déjà dans Django.
- Anti-bruteforce : =django-axes=, paramétrable par variables
  d'environnement (voir § 3.5).
- UI mot de passe : JavaScript vanilla (bouton afficher/masquer),
  cohérent avec l'absence de framework frontend du projet.
- 2FA : =django-otp= + =qrcode=, activable par compte.

* 3. Décisions retenues

** 3.1 Fournisseur d'e-mail

Backend SMTP générique natif de Django, sans lien figé à un fournisseur.
=django-anymail= reste une extension facultative pour SendGrid, Mailgun,
Postmark, Brevo… et n'impacte pas le code appelant. Un déploiement sans
courriel reste possible s'il est choisi explicitement ; les invitations
sont alors transmises manuellement et le self-service de réinitialisation
est indisponible.

** 3.2 Domaine d'envoi

=Ouvert=. Pas de domaine dédié pour le prototype actuel ; les futurs
hébergeurs du pilote devraient en fournir un. Tant qu'aucun domaine
avec SPF/DKIM n'est disponible, les e-mails d'invitation risquent
d'être classés indésirables — point à vérifier avant la mise en
service du Jalon 2 chez un hébergeur donné.

** 3.3 Authentification à deux facteurs

Décision révisée le 4 octobre 2026. L'interrupteur par compte envisagé
d'abord est remplacé par une politique hiérarchique : le déployeur, puis
l'école, rendent le 2FA obligatoire jusqu'à un rang de fonction, ou le
désactivent à partir d'un rang ; entre les deux, il reste optionnel. Une
obligation reçue du dessus ne se baisse pas, une désactivation reçue du
dessus ne se rouvre pas, comme pour les choix de bases en =#R4=. Le détail
des règles figure au § 6.7. Rien de cela n'est encore implémenté : le 2FA
reste absent de l'application et n'est pas activé par défaut.

** 3.4 Lien d'invitation affiché une fois

Conservé comme canal de secours après la mise en place de l'e-mail
(Jalon 2), plutôt que retiré :

- ce n'est pas l'affichage ponctuel qui est risqué (rien n'est
  journalisé ni re-consultable) ;
- le risque réel — un jeton porteur circulant hors bande — existe
  quel que soit le canal de transmission, e-mail compris ;
- utile en secours si l'envoi d'e-mail échoue, ou si la direction
  préfère transmettre en main propre pour une raison locale.

** 3.5 Anti-bruteforce, paramétrable par déploiement

Retenu : =django-axes=, avec des seuils lus depuis l'environnement
(même pattern que =CARNET_HOSTS=, =CARNET_DEBUG=, etc.), pour permettre
des réglages différents entre la démonstration publique Render et un
futur pilote réel.

#+begin_src python
# carnet/settings.py
AXES_FAILURE_LIMIT = int(os.environ.get("CARNET_CONNEXION_TENTATIVES_MAX", "5"))
AXES_COOLOFF_TIME = timedelta(
    minutes=int(os.environ.get("CARNET_CONNEXION_BLOCAGE_MINUTES", "15"))
)
AXES_LOCKOUT_PARAMETERS = [["ip_address", "username"]]
#+end_src

Valeurs par défaut proposées :

| Déploiement                          | Tentatives max | Blocage    | Justification                                                        |
|----------------------------------------+-----------------+------------+------------------------------------------------------------------------|
| Démonstration publique (Render)        | 10              | 5 minutes  | Données fictives, usage exploratoire par des visiteurs multiples ; on privilégie la fluidité |
| Pilote (données réelles d'école)       | 5               | 15 minutes | Données d'enfants réelles ; seuil aligné sur les pratiques usuelles   |

=ENVIRONNEMENT_ATELIER= et =ENVIRONNEMENT_EPHEMERE=, déjà présents
dans =settings.py=, peuvent fixer les valeurs par défaut
automatiquement ; les variables =CARNET_CONNEXION_*= restent la voie
de surcharge explicite par déploiement.

** 3.6 Priorité et urgence

Aucun jalon n'est bloquant à court terme, mais le démarrage est
souhaité dès maintenant plutôt que reporté.

* 4. Feuille de route

Suite de la série =#C= ouverte par ce document (=#C1=). Ordre
recommandé : =1 → 2 → 3 → 4 → 5 → 6 → 7 → 8=. Le jalon 4 est
détachable et peut être traité en parallèle des autres.

** Jalon 1 — #C2 Infrastructure e-mail (fondation)

- Configurer =EMAIL_BACKEND= dans =settings.py= via l'environnement, ou
  exiger une désactivation explicite du courriel en production.
- Proposer =django-anymail= dans un fichier de dépendances facultatif et
  configurer =ANYMAIL= uniquement pour les prestataires concernés.
- Ajouter =DEFAULT_FROM_EMAIL=.
- Gabarit d'e-mail HTML/texte minimal, sobre.
- Vérifier la configuration DNS (SPF/DKIM) dès qu'un domaine est
  disponible (§ 3.2).
- Livrable : commande de test d'envoi, vérifiée en local puis sur
  chaque déploiement.

** Jalon 2 — #C3 E-mail d'invitation

- Dans =inviter()= (=suivi/services/equipe.py=), envoyer l'e-mail
  avec le lien déjà construit, juste après la création de
  l'=Invitation=.
- Garder l'affichage du lien en session comme filet de secours
  (§ 3.4) ; journaliser un échec d'envoi.
- Adapter le message de succès dans =equipe_ecole= : « l'invitation a
  été envoyée à *email* » plutôt que « copiez le lien ».
- Tests : backend =locmem= en test, vérification du contenu et du
  lien généré.
- Dépend de : Jalon 1.

** Jalon 3 — #C4 Mot de passe oublié (self-service)

- Brancher =PasswordResetView=, =PasswordResetDoneView=,
  =PasswordResetConfirmView=, =PasswordResetCompleteView= dans
  =suivi/urls.py=.
- Quatre templates sobres, dans le style de =connexion.html=.
- Lien « mot de passe oublié » ajouté sur =connexion.html=.
- Dépend de : Jalon 1 (réutilise le même backend mail).

** Jalon 4 — #C5 UX du champ mot de passe (indépendant)

- Bouton « afficher en clair » en JavaScript vanilla sur les champs
  =password1=/=password2=/=mot_de_passe=.
- Aide contextuelle basée sur =AUTH_PASSWORD_VALIDATORS= déjà en
  place (aucun changement de validation, seulement d'affichage).
- Appliqué aux trois formulaires concernés : connexion, création de
  compte par invitation, futur reset.

** Jalon 5 — #C6 Anti-bruteforce et audit des connexions

- =django-axes= sur la vue =connexion= et la branche connexion de
  =accepter_invitation_vue=, avec seuils paramétrés par déploiement
  (§ 3.5).
- Étendre =journaliser()=/=EvenementAudit= pour accepter un
  événement sans école (ou journal de connexions séparé), afin de
  tracer les échecs — actuellement invisibles.
- Logiquement après le Jalon 3 (sinon un compte bloqué sans reset
  disponible laisse l'utilisateur sans issue).

** Jalon 6 — #C7 Bascule vers les vues de connexion standard Django — abandonné

Envisagé initialement pour deux raisons : moins de code maison, et une
meilleure compatibilité avec =django-axes=. La seconde raison a disparu
avec le Jalon 5 (#C6) : =connexion()= appelle déjà =authenticate(request,
...)=, ce qui suffit à =axes= — vérifié par les tests d'anti-bruteforce.

Reste le bénéfice de code, mais =connexion()= a grossi au fil des
jalons précédents (redirection du mode local, distinction membre sans
fonction, retour sur la page demandée) : =LoginView.form_valid()=
appelle lui-même =login()=, donc le reprendre demanderait de le
surcharger presque entièrement, pour un gain surtout esthétique et un
risque de régression réel — notamment en mode local, non testable
ici. Décision : conserver =connexion()= telle quelle.

À la place, correctif d'ergonomie ciblé : l'identifiant saisi est
conservé après un échec de connexion (jamais le mot de passe), avec le
focus reporté sur le champ mot de passe — pour ne pas avoir à tout
retaper, ce qui compte double une fois l'anti-bruteforce en place.

** Jalon 7 — #C8 2FA pour la direction et le personnel

Conception arrêtée le 4 octobre 2026 (§ 3.3 et § 6.7), livrée en
sous-étapes : =#C8a= conception, =#C8b= politique et exigence effective,
=#C8c= inscription TOTP et vérification à la connexion, =#C8d= codes de
secours et réinitialisation, =#C8e= écrans de la direction, diagnostic et
documentation de déploiement.

** Jalon 8 — #C9 Cosmétique

- Tâche planifiée (commande =manage.py= + cron ou tâche planifiée
  côté hébergeur) pour marquer =EXPIREE= les invitations dont
  =expire_le= est dépassé, plutôt que de le calculer dynamiquement au
  template.

* 5. Points encore ouverts

- Domaine d'envoi et accès DNS pour SPF/DKIM (§ 3.2).
- Confirmation que Render (et le futur hébergeur du pilote)
  autorisent l'envoi SMTP sortant, ou nécessitent une passerelle API
  (=django-anymail= gère les deux cas).
- Choix définitif du fournisseur d'e-mail transactionnel.
- Adresse IP des clients derrière un reverse-proxy : traitée par
  =CARNET_PROXYS_NB= (§ 6.6), mais la valeur exacte reste à établir et à
  vérifier avec chaque hébergeur réel, selon la procédure de
  =DEPLOIEMENT.org=.
- Cache partagé pour les compteurs de limitation de fréquence : non
  configurable aujourd'hui (§ 6.4), à traiter seulement si un hébergeur
  impose plusieurs workers.
- 2FA (§ 6.7) : la politique de l'école n'a pas encore d'écran (=#C8e=) ; en
  attendant, seul le déployeur la fixe, par variables d'environnement. Une
  réinitialisation ne ferme pas les sessions déjà ouvertes du compte : elle
  efface la clé et les codes, pas les sessions (à traiter si le besoin
  apparaît). Sort de la clé d'une personne dont la fonction devient
  désactivée : elle est conservée, inactive (le code n'est plus demandé).

Un ajout hors feuille de route initiale : la **pré-attribution d'une
fonction dès l'invitation** (§ 6.2), née d'un audit intermédiaire sur
le blocage de connexion d'un compte fraîchement créé sans affectation.

** 6.2 Pré-attribution — résumé pour ce document

=AffectationClasse.appartenance= est devenue optionnelle ; une
=AffectationClasse.invitation= facultative permet à la direction de
préattribuer une fonction (classe + rôle) au moment de l'invitation,
avant même que le compte existe. =est_active()= renvoie toujours
=False= tant que =appartenance= est =None= : aucun accès réel n'est
jamais accordé prématurément. À l'acceptation, la pré-attribution est
promue automatiquement (=appartenance= renseignée), et la personne
peut se connecter immédiatement.

Affichée avec un badge « Invitation en cours » (couleur =--en-cours=,
déjà dans la charte) dans la vue « classes » et sur la page
Collaborateurs d'une classe ; annulable par la direction comme une
affectation ordinaire, sans obligation de remplacement (elle ne compte
de toute façon pas comme un responsable actif). Limites assumées :
préattribution possible uniquement au moment de l'invitation (pas
d'ajout après coup sur une invitation déjà en attente), absente de la
vue « personnes », et =remplacer_responsable()= non étendu aux
invitations.

** 6.3 Captcha ou autre frein aux automatismes ?

Revue des surfaces exposées sans authentification :

- *Connexion* (=connexion()=, branche =compte_existant= de
  l'acceptation d'invitation) : protégée par =django-axes= depuis le
  Jalon 5. Un captcha n'apporterait rien de plus contre la devinette
  de mot de passe.
- *Lien d'invitation* : jeton à 256 bits d'entropie, jamais indexable
  par force brute quel que soit le débit d'essais.
- *Demande de réinitialisation de mot de passe*
  (=mot_de_passe_oublie=) : =PasswordResetForm= ne révèle jamais si
  l'adresse existe (comportement Django standard), donc pas de risque
  d'énumération de comptes ; le risque était la nuisance (bombardement
  d'e-mails vers une adresse qu'on ne possède pas). Traité par
  =django-ratelimit= (§ 6.4), plutôt qu'un captcha ou que détourner
  =django-axes=, conçu pour des tentatives d'authentification avec
  succès/échec, pas un simple comptage de requêtes.
- *Création de compte* : jamais publique, seulement via un jeton
  d'invitation à haute entropie.

Décision : pas de captcha, disproportionné pour une application
d'école sans registre public et déjà protégée où ça compte
(connexion) — et ça évite une dépendance à un service tiers
(reCAPTCHA/hCaptcha), avec ses propres questions RGPD pour un usage en
école.

** 6.4 Limitation de fréquence sur la demande de réinitialisation

=django-ratelimit= limite les requêtes =POST= vers
=mot_de_passe_oublie= par adresse IP (=CARNET_RATELIMIT_MOT_DE_PASSE_OUBLIE=,
=5/h= par défaut). Au-delà, un message dédié s'affiche plutôt que le
formulaire, sans jamais bloquer la connexion elle-même (surface
distincte de =django-axes=).

Limite connue : le compteur utilise le cache Django par défaut, c'est-à-dire
la mémoire locale du processus. Aucun cache partagé n'est configurable
aujourd'hui (une variable =CARNET_CACHE_URL= a été mentionnée à tort dans une
version antérieure de ce paragraphe ; elle n'existe pas). Les compteurs
repartent de zéro au redémarrage et, avec plusieurs workers gunicorn, chacun
compte de son côté ; les scripts de démarrage n'en lancent qu'un par défaut,
auquel cas le compteur est global au déploiement. Suffisant comme frein de
nuisance, pas une garantie stricte multi-worker. =django-ratelimit= n'officialise
que memcached et Redis (le cache en base est déclaré non atomique) : une
évolution demanderait une dépendance et un réglage de =CACHES=.

** 6.5 Changement de mot de passe pour un compte connecté

Page =mon-compte/mot-de-passe/= (=changer_mot_de_passe=), liée depuis
=mon_compte.html=, protégée par =acces_requis=. Elle s'appuie sur
=PasswordChangeView= de Django : ancien mot de passe exigé, mêmes
validateurs que partout ailleurs (dont longueur minimale 12), bouton
« afficher » du Jalon 4 appliqué automatiquement.

Après un changement, la personne reste connectée sur son navigateur
(=update_session_auth_hash=) ; ses autres sessions ouvertes sont
invalidées, ce qui est le comportement voulu si le changement fait suite
à un doute sur le compte.

La vérification de l'ancien mot de passe passe par =check_password=, pas
par =authenticate()= : =django-axes= ne la voit donc pas. Elle est
plafonnée par compte avec =django-ratelimit=
(=CARNET_RATELIMIT_CHANGEMENT_MOT_DE_PASSE=, =10/h= par défaut), avec la
même limite de cache par worker que le § 6.4. Au-delà, une réponse 429
affiche un message dédié, sans toucher à la connexion elle-même.

** 6.6 Adresse IP des clients derrière un reverse-proxy (#C11)

Constat : =django-axes= (=AXES_LOCKOUT_PARAMETERS= sur adresse + identifiant)
et le plafond du mot de passe oublié (=key="ip"= de =django-ratelimit=) ne
lisaient que =REMOTE_ADDR=, soit l'adresse du proxy derrière tout hébergeur
réel. Le blocage se réduisait alors à l'identifiant seul (un tiers pouvait
bloquer un compte ciblé) et le plafond était commun à tous les visiteurs.

Décision : une fonction unique, =carnet.reseau.adresse_client=, réglée par
=CARNET_PROXYS_NB= (0 par défaut : comportement inchangé). Avec N proxys de
confiance qui complètent chacun =X-Forwarded-For=, le client est la N-ième
entrée en partant de la droite. Elle est branchée sur =django-axes=
(=AXES_CLIENT_IP_CALLABLE=), sur le plafond du mot de passe oublié et sur la
ligne de journal des échecs de connexion, de sorte que les trois voient la
même adresse. Elle n'ajoute aucune dépendance (le module =ipware= n'est pas
utilisé) et fonctionne aussi sans =django-axes= (installation autonome).

Le réglage est dangereux s'il est trop grand : la N-ième entrée à partir de la
droite sort alors de la zone ajoutée par les proxys et le client peut la
forger. Il n'est donc jamais activé par défaut, documenté avec une procédure
de vérification dans =DEPLOIEMENT.org=, et un test fige ce comportement. Le
diagnostic de déploiement avertit (sans jamais échouer) lorsque HTTPS est forcé
sans =CARNET_PROXYS_NB=, et lorsque l'expéditeur des courriels est l'adresse
fictive par défaut.

** 6.7 Conception du 2FA hiérarchique (#C8a, 4 octobre 2026)

État : décisions arrêtées avec Emmanuel. =#C8a= les consigne ; =#C8b= implémente
la politique (variables du déployeur, politique de l'école, rangs, exigence
effective) ; =#C8c= l'applique : second facteur TOTP à la connexion, échéance
d'inscription, inscription et retrait volontaire ; =#C8d= ajoute les codes de
secours et la réinitialisation. Les écrans de la direction pour la politique de
l'école n'existent pas encore.

*** Périmètre et échelle

Deux niveaux posent une politique : le déployeur (hébergeur ou DSI) et
l'école. Il n'y a pas de niveau classe : le 2FA protège un compte, qui est
indépendant de toute classe. Les populations forment une échelle ordonnée :

| Rang | Population                                            |
|------+-------------------------------------------------------|
|    1 | direction                                             |
|    2 | responsables de classe                                |
|    3 | enseignants associés                                  |
|    4 | contributeurs                                         |
|    5 | personnes authentifiées sans fonction                 |

*** Deux curseurs par niveau

- /obligatoire jusqu'au rang n/ (0 : personne) : le 2FA est exigé pour les
  rangs inférieurs ou égaux à n ;
- /désactivé à partir du rang m/ (6 : jamais) : le 2FA est retiré pour les
  rangs supérieurs ou égaux à m ;
- entre les deux, il est optionnel ; on exige n < m à chaque niveau.

Héritage : n effectif = max(n du dessus, n propre) et m effectif = min(m du
dessus, m propre). Une école ne peut donc ni baisser une obligation du
déployeur, ni rouvrir ce que le déployeur a désactivé. Elle peut durcir, ou
désactiver là où rien n'est obligatoire au-dessus. L'interface refuse toute
valeur qui violerait ces règles. =CARNET_MODE_LOCAL= équivaut à une
désactivation du déployeur dès le rang 1.

*** Comptes rattachés à plusieurs écoles

Le rang se lit par école. L'obligation l'emporte : si une seule école
l'exige pour le rang de la personne, le compte est obligé. La fonction n'est
retirée que si toutes ses écoles la désactivent pour son rang. Une personne
sans aucune appartenance active n'est soumise qu'à la politique du
déployeur. L'exigence est toujours calculée à partir des rattachements et
fonctions actifs, jamais stockée.

*** Cycle de vie

- Délai de grâce unique, fixé par le déployeur
  (=CARNET_2FA_DELAI_GRACE_JOURS=, valeur par défaut de l'application
  proposée : 14 jours, 0 pour une application immédiate, plafond proposé :
  90). Il court à partir du premier accès où l'obligation est constatée, de
  sorte que les vacances scolaires ne le consomment pas. Passé ce délai,
  l'accès est bloqué jusqu'à l'inscription. L'école ne règle pas ce délai.
- Un compte neuf créé par invitation et déjà soumis à l'obligation s'inscrit
  dès sa création, sans délai de grâce.
- Hors obligation, une personne déjà inscrite garde son 2FA et peut le
  retirer elle-même, en présentant un code valide. Si sa fonction devient
  désactivée, le second facteur n'est plus demandé.

*** Mécanique

- TOTP avec =django-otp= et =qrcode=, en dépendances facultatives (comme
  =django-anymail=), absentes du paquet autonome.
- Clé secrète stockée chiffrée, avec une clé dédiée au déploiement (pas
  dérivée de =CARNET_SECRET_KEY=, dont la rotation casserait tous les
  comptes), ce qui ajoute la dépendance =cryptography=, absente de
  =requirements.lock= aujourd'hui.
- Dix codes de secours à usage unique, conservés sous forme d'empreintes
  seules (comme les jetons d'invitation), régénérables par la personne,
  chaque usage journalisé.
- Tolérance d'horloge de plus ou moins un pas de 30 secondes, un code déjà
  accepté ne pouvant pas être rejoué.
- Les saisies du code TOTP et des codes de secours ne passent pas par
  =authenticate()= : =django-axes= ne les voit pas. Elles sont plafonnées par
  compte avec =django-ratelimit=, l'adresse du client venant de
  =carnet.reseau.adresse_client=.
- « Mot de passe oublié » ne touche pas au second facteur : après une
  réinitialisation, le code reste demandé. La branche « compte existant » de
  l'acceptation d'invitation passe par le même contrôle.
- Le diagnostic de déploiement avertit seulement (obligation configurée sans
  clé de chiffrement ou sans les dépendances), sans jamais faire échouer un
  profil existant.

*** Politique : où elle vit

Le déployeur la fixe par variables d'environnement à valeurs nommées (par
exemple une obligation « direction » et une désactivation « contributeur »
et en dessous), cohérentes avec les autres réglages du déployeur. La
politique de l'école est en base, avec révision attendue et journalisation,
modifiable par la direction, comme les choix de bases de =CHOIX-BASES-REFERENTIELS.org=.

*** Récupération

La direction réinitialise le 2FA des personnes dont le rang est strictement
inférieur au sien, comparé au plus haut rang du compte toutes écoles
confondues : une direction ne peut pas affaiblir un compte qui est aussi
direction ailleurs. Dans les autres cas, y compris pour la direction,
l'intervention est celle du déployeur, par commande. Une réinitialisation
n'annule jamais l'obligation : la personne se réinscrit à sa connexion
suivante.

*** Précisions de l'implémentation (#C8b)

- Rang d'un compte dans une école : direction (responsabilité active), puis le
  type d'affectation de classe le plus haut, sinon « sans fonction ». Il suit
  l'accès réellement accordé : une affectation sur une classe encore en
  préparation, ou une pré-attribution d'invitation, ne donne pas encore de rang.
- Variables du déployeur : =CARNET_2FA_OBLIGATOIRE= et =CARNET_2FA_DESACTIVE_POUR=,
  à valeurs nommées. Une valeur non reconnue ou incohérente empêche le
  démarrage (=ImproperlyConfigured=), pour qu'une faute de frappe ne supprime
  pas une obligation sans bruit ; absentes, elles ne changent rien.
  =CARNET_MODE_LOCAL= impose l'indisponibilité.
- Politique de l'école : =PolitiqueDoubleFacteurEcole= (une ligne par école,
  contraintes en base sur les bornes et sur n < m), révision attendue,
  journal =securite.double_facteur_ecole=, réservée à la direction active
  (opération =ADMINISTRER_ECOLE=). L'enregistrement refuse une intention
  contraire au déployeur (rendre obligatoire ce qu'il désactive, désactiver ce
  qu'il impose) mais accepte une valeur moins stricte que lui, qui reste sans
  effet : une valeur héritée n'est ainsi pas recopiée comme un choix propre.
- Si le déployeur change ensuite ses curseurs, le niveau supérieur l'emporte :
  la politique effective écarte la part incompatible de celle de l'école et le
  signale par un avertissement, sans rien modifier en base.

*** Précisions de l'implémentation (#C8c)

- Fonction facultative : elle n'existe que si =requirements-2fa.txt= est
  installé, =CARNET_2FA_CLE= renseignée et hors =CARNET_MODE_LOCAL=. Sinon la
  politique du déployeur est neutre (désactivée pour tous) et rien ne change.
  Demander le 2FA sans ses dépendances, ou l'obligation sans clé, empêche le
  démarrage ; une obligation posée par une école est refusée si la fonction est
  indisponible.
- =django-otp= ne sert qu'au calcul des codes (=django_otp.oath=), sans ses
  modèles ni son middleware : la clé étant chiffrée, son modèle de dispositif ne
  convient pas. Le stockage est propre à l'application (=DoubleFacteurCompte=,
  clé chiffrée avec Fernet, dernier pas accepté, échéance).
- Un compte inscrit n'obtient *aucune session* avant son second facteur : la
  connexion s'arrête avant =login()= (attente de 5 minutes en session), et un
  middleware ferme toute session née sans second facteur. Une fonction
  désactivée ne demande plus de code.
- Saisies de code plafonnées par compte et par adresse (=django-ratelimit=,
  adresse =carnet.reseau.adresse_client=), comme l'ancien mot de passe en
  =#C10= ; =django-axes= ne les voit pas.
- Échéance : posée au premier constat de l'obligation (délai de grâce du
  déployeur), effacée si l'obligation cesse, immédiate pour un compte créé par
  invitation. Passée l'échéance, un compte non inscrit ne peut plus que
  configurer son second facteur ou se déconnecter.
- L'exigence est recalculée au plus toutes les 60 secondes par session : un
  changement de politique peut mettre jusqu'à une minute à s'appliquer.

*** Précisions de l'implémentation (#C8d)

- Codes de secours : dix codes de seize caractères (alphabet de 32 sans
  ambiguïté, 80 bits), à usage unique, conservés sous forme d'empreinte SHA-256
  seule, affichés une seule fois (à l'inscription, puis à chaque régénération,
  qui invalide les précédents). La régénération exige un code actuel de
  l'application : un code de secours ne suffit pas. Saisis à la connexion dans
  le même champ que le code TOTP, sous le même plafond de tentatives. Chaque
  usage prévient la personne (codes restants, rappel quand il en reste peu) et
  est journalisé dans chaque école où elle est active.
- Réinitialisation par la direction (écran d'équipe) : réservée à la direction
  de l'école, pour un membre de cette école qui a un second facteur, dont le
  plus haut rang toutes écoles confondues est strictement inférieur à celui de
  direction ; jamais pour soi-même. Une direction, ou un compte direction dans
  une autre école, relève du déployeur. Journal =securite.double_facteur_reinitialise=
  dans l'école de la direction.
- Réinitialisation par le déployeur : commande =reinitialiser_double_facteur=
  (=--utilisateur=, =--operateur= compte technique actif, =--motif=), pour tout
  compte, direction comprise ; journalisée dans chaque école du compte. Elle
  fonctionne même si la fonction est indisponible.
- Une réinitialisation efface la clé et les codes mais *jamais l'obligation* :
  si elle s'applique encore, la personne est invitée à se réinscrire dès sa
  connexion suivante, sans nouveau délai de grâce ; sinon la connexion ne
  demande plus de code.
