#+title: Contrat de déploiement persistant de Petits Pas

* Objet

Ce document décrit les ressources et réglages attendus par le profil
persistant de Petits Pas. Il sert d’interface entre l’application et
l’hébergeur ; il ne prescrit ni fournisseur, ni orchestrateur particulier.

Le fichier =.env.example= récapitule les variables sous une forme directement
lisible. Django ne charge pas automatiquement ce fichier : les variables et
secrets doivent être injectés par la plate-forme de déploiement.

* Ressources nécessaires

- une base PostgreSQL joignable par l’application ;
- un bucket privé compatible avec l’API S3 ;
- un proxy HTTPS transmettant =X-Forwarded-Proto: https= ;
- un mécanisme externe de sauvegarde et de rétention.

Le bucket doit exister avant le démarrage. Les identifiants de l’application
doivent permettre au minimum la création, la lecture et la suppression
d’objets dans ce bucket. Aucun média ne doit être rendu public : Django génère
des URL temporaires signées.

* Variables d’environnement

** Obligatoires

- =DATABASE_URL= : URL de connexion PostgreSQL ;
- =CARNET_S3_BUCKET= : nom du bucket réservé aux médias ;
- =CARNET_SECRET_KEY= : valeur longue, aléatoire et stable ;
- =CARNET_DEBUG=0= : désactive les pages d’erreur détaillées ;
- =CARNET_HOSTS= : noms DNS acceptés, séparés par des virgules ;
- =CARNET_CSRF_ORIGINS= : origines HTTPS complètes, séparées par des virgules.
- =CARNET_FORCER_HTTPS=oui= : redirection HTTPS et cookies sécurisés.

Lorsque =CARNET_FORCER_HTTPS=oui=, Django force HTTPS et marque les cookies de
session et CSRF comme sécurisés. L'en-tête =X-Frame-Options= interdit par ailleurs
l'intégration des écrans dans un site tiers. HSTS reste à activer au niveau de
l'hébergeur une fois le domaine HTTPS définitif validé : l'activer trop tôt
peut rendre un retour en arrière difficile.

** Selon le fournisseur S3

- =CARNET_S3_ENDPOINT_URL= : URL de l’API pour un service compatible S3 ;
- =CARNET_S3_REGION= : région du bucket ;
- =CARNET_S3_ACCESS_KEY= et =CARNET_S3_SECRET_KEY= : identifiants statiques.

Les identifiants statiques peuvent être omis lorsque la plate-forme fournit un
autre mécanisme d’authentification compris par Boto3.

** Facultatives

- =CARNET_S3_URL_EXPIRATION= : durée de validité des URL signées, en secondes
  (300 par défaut) ;
- =PORT= : port d’écoute de Gunicorn (8000 par défaut).

* Construction et démarrage

Les déploiements ordinaires installent les versions validées depuis
=requirements.lock=. Les plages de compatibilité restent décrites séparément
dans =requirements.txt= ; voir =REPRODUCTIBILITE.org=.

La génération PDF utilise WeasyPrint. L'image ou le système d'exécution doit
donc fournir ses bibliothèques natives de composition typographique et de rendu
en plus des paquets Python de =requirements.lock=. Le paquet Guix
=weasyprint= fournit cet ensemble pour le développement ; la disponibilité de
la commande suivante doit être contrôlée chez l'hébergeur :

#+begin_src sh
weasyprint --info
#+end_src

La commande de démarrage du profil persistant est :

#+begin_src sh
./start-persistent.sh
#+end_src

Avant de lancer Gunicorn, ce script :

- refuse une configuration qui ne satisfait pas les garde-fous du profil ;
- applique les migrations Django ;
- rassemble les fichiers statiques pour WhiteNoise ;
- écrit, relit puis supprime un objet de contrôle dans le bucket.

Une erreur à l’une de ces étapes doit faire échouer le déploiement. Le script
ne crée aucune école et ne charge aucune donnée métier.

* Sondes

La sonde non authentifiée =GET /health/= renvoie :

- =200 {"status": "ok"}= lorsque Django peut interroger PostgreSQL ;
- =503 {"status": "unavailable"}= lorsque la base est indisponible.

Elle ne révèle ni exception, ni nom de base, ni secret et ne contacte pas S3.
La connexion S3 est contrôlée au démarrage par =verifier_stockage_objet=.

* Initialisation fonctionnelle

La création d’une école et le chargement de son référentiel restent des
opérations explicites :

#+begin_src sh
python manage.py creer_ecole "Nom de l’école" --commune "Commune"
python manage.py charger_referentiel referentiel/trame-cycle1.yaml
#+end_src

=jeu_demo= ne doit être utilisé qu’avec des données factices.

L'atelier pédagogique persistant possède une initialisation dédiée et des
garde-fous supplémentaires. Sa procédure complète est décrite dans
=ATELIER-PEDAGOGIQUE.org= ; elle ne doit pas être confondue avec celle d'un
futur pilote comportant des données réelles.

* Sauvegardes et restaurations

** PostgreSQL

La sauvegarde PostgreSQL peut être déclenchée avec :

#+begin_src sh
export CARNET_BACKUP_DIR=/chemin/absolu/vers/un/stockage/durable
scripts/sauvegarder-postgresql.sh
#+end_src

Ce répertoire doit être distinct du système de fichiers éphémère de
l’application. La restauration doit être testée périodiquement dans une base
séparée avec les scripts documentés dans =README-carnet-v0.md=.

** Médias

Petits Pas peut exporter les médias depuis tout backend Django, y compris S3,
vers un répertoire durable indépendant :

#+begin_src sh
export CARNET_BACKUP_DIR=/chemin/absolu/vers/un/stockage/durable
scripts/sauvegarder-medias.sh
#+end_src

Chaque sauvegarde contient les objets sous leur nom logique et un manifeste
JSON indiquant leur taille et leur somme SHA-256. Elle peut être vérifiée sans
accéder au stockage d’origine :

#+begin_src sh
python manage.py verifier_sauvegarde_medias \
  /chemin/petits-pas-medias-YYYYMMDDTHHMMSSZ
#+end_src

La restauration vérifie d’abord toute la sauvegarde et refuse d’écraser un
objet existant :

#+begin_src sh
export CARNET_AUTORISER_RESTAURATION_MEDIAS=oui
scripts/restaurer-medias.sh \
  /chemin/petits-pas-medias-YYYYMMDDTHHMMSSZ
#+end_src

Cette copie portable complète, sans les remplacer, les mécanismes fournis par
l’hébergeur : versionnement du bucket, réplication vers un autre stockage,
rétention et protection contre la suppression du bucket ou du compte.

** Cohérence d’un point de reprise

Les sauvegardes PostgreSQL et médias réalisées séparément ne constituent pas
un instantané atomique : une modification peut survenir entre les deux. Pour
le pilote avec données factices, elles peuvent être exécutées successivement.
Une future production devra prévoir une courte mise en maintenance ou un
mécanisme de snapshots coordonnés fourni par l’hébergeur, en fonction de
l’objectif de reprise retenu.

Petits Pas peut regrouper les deux exports dans un paquet de reprise vérifiable.
En mode =online=, PostgreSQL est sauvegardé avant les médias ; le manifeste
indique explicitement que l’ensemble n’est pas atomique :

#+begin_src sh
export CARNET_BACKUP_DIR=/chemin/absolu/vers/un/stockage/durable
scripts/sauvegarder-reprise.sh online
#+end_src

Le mode =writes-suspended= qualifie le paquet comme logiquement cohérent, mais
il repose sur une garantie fournie par l’opérateur : toutes les écritures et
requêtes en cours doivent être arrêtées pendant l’opération.

#+begin_src sh
export CARNET_BACKUP_DIR=/chemin/absolu/vers/un/stockage/durable
export CARNET_ECRITURES_SUSPENDUES=oui
scripts/sauvegarder-reprise.sh writes-suspended
#+end_src

Le script construit le paquet sous un nom temporaire, vérifie l’archive
PostgreSQL, les médias et le manifeste global, puis publie le répertoire final
par renommage. Un paquet existant se vérifie indépendamment avec :

#+begin_src sh
scripts/verifier-reprise.sh \
  /chemin/petits-pas-reprise-YYYYMMDDTHHMMSSZ
#+end_src

La restauration reste volontairement composée des procédures PostgreSQL et
médias séparées : aucune transaction commune ne permettrait de les annuler
ensemble en cas d’échec.

** Exercice complet de reprise

Une sauvegarde n’est considérée comme exploitable qu’après un essai de
restauration. Pour le profil local natif, un paquet coordonné peut être restauré
dans une base PostgreSQL nouvellement créée et un répertoire de médias vide :

#+begin_src sh
source scripts/activer-local-natif.sh
scripts/exercer-reprise-local.sh \
  "$PWD/backups/petits-pas-reprise-YYYYMMDDTHHMMSSZ"
#+end_src

L’exercice :

- vérifie le paquet avant toute restauration ;
- crée une base portant un nom unique, distincte de la base active ;
- restaure PostgreSQL et les médias vers des cibles temporaires ;
- vérifie les migrations, la lecture des données et la présence de chaque
  média référencé par une observation ;
- supprime les deux cibles à la fin, y compris après un échec.

=CARNET_CONSERVER_REPRISE_LOCALE=oui= désactive le nettoyage afin de permettre
une inspection manuelle. Cette option laisse volontairement une base et des
fichiers contenant les données restaurées ; ils doivent alors être supprimés
explicitement par l’opérateur.

Ce mécanisme teste la restaurabilité du paquet. Il ne transforme pas un paquet
=online= en instantané atomique et ne remplace pas un exercice périodique dans
l’infrastructure de l’hébergeur.

** Déploiement éphémère en intégration continue

Le job GitLab =deploiement-ephemere= démarre PostgreSQL et MinIO dans des
services isolés, puis exécute le profil persistant complet. Il vérifie :

- les migrations et la collecte des fichiers statiques ;
- le démarrage de Gunicorn et la sonde =/health/= ;
- l’écriture, la lecture et la suppression sur le stockage S3 ;
- la présence d’un média réellement référencé en base ;
- la création d’un paquet coordonné PostgreSQL + médias ;
- la restauration de ce paquet dans des cibles temporaires distinctes.

Le script refuse de s’exécuter sans
=CARNET_ENVIRONNEMENT_EPHEMERE=oui=. Cette confirmation ne doit être fournie
que pour une base et un bucket jetables. Le succès du job prouve la
reproductibilité du déploiement et de la reprise, mais pas la persistance entre
deux jobs CI ni les garanties du futur hébergeur.

* Recréer la démonstration publique

La démonstration Render ne contient que des données fictives et ne doit être
rattachée ni à PostgreSQL ni à S3. Pour la recréer, arrêter l'application,
supprimer uniquement son fichier local =carnet.sqlite3= et son répertoire
=media/=, puis relancer =./start-render.sh=. Le script applique les migrations,
crée les deux comptes individuels publics décrits dans
=site/data/demonstration.yaml=, recharge le référentiel et génère les jeux de
démonstration pédagogique et d'équipe. Les profils supplémentaires sont tous
fictifs et utilisent, dans cette seule démonstration publique, le mot de passe
enseignant affiché par le site.

Ne jamais utiliser cette procédure sur l'atelier ou le pilote : leur remise à
zéro passe par une sauvegarde préalable et par des ressources PostgreSQL/S3
explicitement identifiées par l'hébergeur.

* Profils

- démonstration éphémère : =start-render.sh=, SQLite, médias sur disque et jeu
  de données recréé. L'URL, le nom de l'école et les identifiants publics sont
  définis dans =site/data/demonstration.yaml=, également lu par le site Hugo.
  =start-render.sh= impose lui-même =CARNET_ENVIRONNEMENT_EPHEMERE=oui= afin
  d'afficher le bandeau d'avertissement ;
- développement local natif : PostgreSQL et médias dans
  =.local-persistent/= ;
- développement local Compose : PostgreSQL et MinIO, variante préparée mais
  pas encore validée sous Podman rootless avec Guix System ;
- intégration continue : PostgreSQL, MinIO et application complète dans des
  services éphémères isolés ;
- atelier pédagogique persistant : =start-atelier.sh=, PostgreSQL et bucket S3
  privés, URL stable et données exclusivement factices ;
- futur pilote ou production : =start-persistent.sh=, PostgreSQL et bucket S3
  privés, seulement après validation des exigences de sécurité et de
  conformité applicables aux données réelles.

Seul le dernier profil représente le contrat destiné à l’hébergeur.
