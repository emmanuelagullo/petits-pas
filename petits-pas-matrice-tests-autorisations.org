* Statut du document

Ce document dérive de :

- =petits-pas-modele-metier-identites-affectations.org= ;
- =ROLES-ET-DROITS.org=.

Il transforme la politique en règles normatives et en scénarios de tests. En
cas de divergence, la politique d'autorisation doit être corrigée ou la
divergence explicitement décidée avant l'implémentation.

* Convention de lecture

** Résultats normatifs

- =A= : opération autorisée ;
- =D= : opération refusée ;
- =C= : autorisée si toutes les conditions indiquées sont satisfaites ;
- =S= : procédure de secours ou exceptionnelle, absente du parcours ordinaire.

** Acteurs

- =PAT= : administration technique de la plateforme ;
- =DIR= : membre de la direction de l'école ;
- =RES= : responsable de la classe concernée ;
- =ASS= : enseignant associé à la classe concernée ;
- =CON= : contributeur de la classe concernée ;
- =MEM= : membre actif de l'école sans responsabilité active ;
- =EXT= : utilisateur sans appartenance à l'école ;
- =ANON= : personne non authentifiée.

Un même utilisateur peut porter plusieurs qualités. Chaque autorisation est
évaluée dans le périmètre précis de l'opération.

* Préconditions universelles

Une opération fonctionnelle exige, sauf indication contraire :

1. un utilisateur authentifié et actif ;
2. une école active ;
3. une appartenance active à cette école ;
4. une responsabilité ou affectation active autorisant l'opération ;
5. une ressource appartenant à la même école ;
6. le respect des bornes temporelles ;
7. le respect des états de la ressource et des contraintes métier.

L'échec d'une précondition entraîne =D= avant toute mutation.

Un refus significatif est un refus révélant une tentative d'élévation de

erreurs ordinaires de formulaire ne sont pas des événements de sécurité.

* Propriétés à tester systématiquement

Au-delà des scénarios nommés, les suites automatisées doivent vérifier les
propriétés suivantes pour chaque opération sensible :

1. même acteur, même rôle, autre école → refus ;
2. même acteur, même école, autre classe → refus sauf permission d'école ;
3. compte suspendu → refus ;
4. appartenance suspendue ou terminée → refus ;
5. affectation future ou expirée → refus ;
6. ressource archivée → mutation refusée sauf opération de réouverture prévue ;
7. identifiant direct forgé → même décision que la navigation normale ;
8. requête HTMX, requête HTML et téléchargement → même décision métier ;
9. opération refusée → aucune mutation partielle ;
10. opération auditée → événement écrit dans la même transaction logique.

* Organisation recommandée des tests Django

Sans figer les noms de modules, séparer au minimum :

- tests unitaires des prédicats d'autorisation ;
- tests des services métier et de leurs invariants ;
- tests d'intégration des vues HTML et HTMX ;
- tests des téléchargements privés ;
- tests de l'audit ;
- tests de non-régression inter-écoles ;
- tests aux bornes temporelles.

Les tests d'autorisation ne doivent pas dépendre seulement de la présence ou de
l'absence d'un bouton dans le HTML. Chaque opération doit être appelée
directement avec des paramètres autorisés et interdits.

* Critère de couverture avant pilote

Avant tout pilote avec données réelles :

- chaque ligne normative doit être couverte par au moins un test positif lorsque
  l'opération est autorisable et un test négatif ;
- chaque opération portant un identifiant d'objet doit avoir un test
  inter-écoles ;
- chaque affectation temporaire doit avoir des tests avant, pendant et après sa
  période ;
- chaque mutation auditée doit vérifier l'événement produit ;
- les téléchargements privés doivent être testés sans dépendre de l'obscurité de
  leur URL ;
- aucune action sensible ne doit reposer uniquement sur le template ou le
  navigateur.

* Étape suivante

Confronter cette matrice au code actuel, identifier les écarts structurants et
produire un plan d'implémentation incrémental avant toute modification du dépôt.
